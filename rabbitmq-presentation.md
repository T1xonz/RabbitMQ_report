# Работа с RabbitMQ

##  Почему заказ не должен ждать отчёта

**Что увидит покупатель, если подготовка документа занимает 30 секунд или сервис обработки временно недоступен?**

- Покупатель оформляет заказ `ORD-1042`. Магазину ещё предстоит подготовить документ и уведомить другие сервисы.
- Если страница ждёт документ, покупатель видит загрузку. При сбое обработчика запрос может закончиться ошибкой или по тайм-ауту.
- Магазин может сразу показать «Заказ принят», а позже обновить статус документа.

---

## Синхронный вызов и работа через очередь

~~~text
Синхронно
Покупатель → API магазина → сервис документов
Покупатель ← API магазина ← результат или ошибка

Через очередь
Покупатель → API магазина → очередь (задание принято)
Покупатель ← «Заказ принят, документ готовится»
                            очередь → обработчик → документ и статус
~~~

- API — часть сайта, которая принимает запросы. В первой схеме она ждёт результат в рамках запроса. Так уместно получать, например, актуальную стоимость доставки перед подтверждением покупки.
- Во второй схеме очередь (queue) хранит принятое задание, пока его некому взять. Покупатель узнаёт о результате позже, например со страницы заказа.
- Приём заказа, подтверждение публикации брокером и завершение фоновой работы — три отдельных события.

---

##  Что такое RabbitMQ и зачем он нужен

- RabbitMQ — брокер сообщений (message broker). Он принимает сообщения, направляет их в очереди и доставляет подключённым обработчикам.
- Обработчик (worker) — отдельная программа. Именно она готовит документ для `ORD-1042`.
- Пока обработчик недоступен, принятое сообщение может ждать в очереди в пределах её настроек.
- Так выносят в фон генерацию документов, отправку уведомлений и обработку изображений. Через брокер также рассылают события между сервисами.

---

## Путь сообщения

~~~text
publisher          → exchange        → queue         → consumer
API магазина         orders.events     order_audit     сервис аудита
EVT-201, ORD-1042    routing key       binding key     читает событие
                     order.created     order.*
~~~

- Отправитель (publisher или producer) публикует сообщение (message) с данными события и задаёт ключ маршрутизации (routing key).
- Обменник (exchange) выбирает маршрут по своему типу и настройкам привязок (bindings) к очередям. Здесь ключ привязки (binding key) `order.*` подходит к `order.created`.
- В очереди (queue) сообщение ждёт доставки. Получатель (consumer) выполняет работу.

---

## Как RabbitMQ выбирает очередь

| Тип exchange | Пример правила | Результат |
| --- | --- | --- |
| `direct` | Точное равенство ключу `document.prepare` | `document.prepare` попадёт в привязанную очередь, `document.cancel` пройдёт мимо |
| `fanout` | Любая привязка, ключ игнорируется | Каждая привязанная очередь получит сообщение |
| `topic` | Шаблон `order.*` | `order.created` подходит, `order.eu.created` пропускается |
| `headers` | `x-match=all`, заголовки `format=pdf` и `region=eu` | Маршрут сработает при совпадении обоих заголовков |

- Обменник по умолчанию (default exchange) — встроенный `direct` с именем `""`. При объявлении очереди RabbitMQ автоматически привязывает её к нему по имени очереди.
- Поэтому `exchange=""` и `routing_key="order_tasks"` ведут в объявленную очередь `order_tasks`.

## Одна задача или событие для нескольких сервисов

~~~text
Задания:  order_tasks → worker-A или worker-B
Событие: orders.events ┬→ order_audit         → сервис аудита
                       └→ order_notifications → сервис уведомлений
~~~

- В одной очереди обработчики конкурируют за задания. Одна доставка задания достаётся одному из них.
- При рассылке обменник может направить одну публикацию в несколько очередей, если совпали их привязки. Дальше каждая очередь обслуживает свой сервис.
- `TASK-101` поручает подготовку документа. `EVT-201` сообщает, что заказ создан.

##  Подтверждения, повторная доставка и дубликаты

~~~text
publisher ←── publisher confirm ── RabbitMQ
                                   RabbitMQ ←── consumer ack ── consumer
~~~

- Подтверждение публикации (publisher confirm) сообщает отправителю, как брокер обработал публикацию. Для проверки наличия маршрута нужен отдельный сигнал возврата через `mandatory`.
- Подтверждение обработки (consumer acknowledgement, `ack`) отправляет обработчик, когда закончил работу.
- Если брокер обнаружит закрытие канала или соединения до получения ручного `ack`, неподтверждённое сообщение может быть доставлено снова. Документ к этому моменту уже может существовать.
- Идемпотентность (idempotency) позволяет повторить попытку без второго документа. Например, храним один документ с уникальным ключом «заказ + тип документа».

##  Первый запуск и веб-интерфейс

~~~text
Python + Pika → 127.0.0.1:5672  → RabbitMQ по AMQP 0-9-1
Браузер       → 127.0.0.1:15672 → Management UI по HTTP
~~~

- AMQP 0-9-1 — протокол, по которому программы обмениваются командами и сообщениями с брокером.
- `Exchanges` показывает обменники и привязки. `Queues and Streams` показывает очереди и потоки.
- `Ready` — ждут доставки. `Unacked` — доставлены, брокер ждёт подтверждения. `Consumers` — зарегистрированные получатели очереди.

##  Очередь фоновых задач

- Отправляем `TASK-101`–`TASK-104` в `order_tasks` без обработчиков. Ожидаем `Ready = 4`.
- Запускаем `worker-A` и `worker-B`. Каждый берёт по одному неподтверждённому сообщению за раз (`prefetch_count=1`). Смотрим разные ID в логах.
- Публикуем `TASK-105` на 60 секунд. По строке `START` находим процесс, смотрим `Unacked = 1` и завершаем этот процесс до `ack`.
- Второй процесс получает `TASK-105` с `redelivered=True` и подтверждает после работы. По одному признаку повторной доставки нельзя узнать, был ли уже создан документ.

##  Маршрутизация событий заказа

`orders.events` — обменник типа `topic`. Привязки создаются до публикации.

| Ключ публикации | `order_audit` · `order.*` | `order_notifications` · `order.created` |
| --- | --- | --- |
| `order.created` · `EVT-201` | Получит | Получит |
| `order.cancelled` · `EVT-202` | Получит | Пропустит |
| `payment.failed` · `EVT-203` | Пропустит | Пропустит |

- Предскажите, в скольких очередях появится `EVT-201`. Сверим прогноз по `Ready` и логам.
- Сегменты ключа разделены точками. `*` совпадает ровно с одним сегментом, `#` — с нулём или несколькими.
- Для `payment.failed` включён `mandatory`. При отсутствии маршрута брокер возвращает сообщение отправителю.

## Аналоги и отличия

| Решение | Типичная задача | Распределение | Повторное чтение | Эксплуатация и ограничение |
| --- | --- | --- | --- | --- |
| RabbitMQ, обычные очереди | Фоновые задачи, рассылка по правилам | Привязки направляют в очереди, обработчики очереди конкурируют | Повторная доставка до `ack` возможна, после `ack` истории для чтения нет | Свой брокер или управляемый сервис. Для отдельной подписки нужна очередь |
| Apache Kafka | Долгоживущий поток событий | Топик разбит на разделы, внутри группы раздел закрепляется за одним участником | По позиции (offset) в пределах хранения | Свой кластер или управляемый сервис. Порядок обеспечивается в пределах раздела |
| Amazon SQS + Amazon SNS | Фоновые задачи и рассылка в AWS | SNS рассылает в подписанные очереди SQS, обработчики в каждой очереди конкурируют | SQS снова делает неудалённое сообщение доступным после тайм-аута видимости. После удаления из SQS повторное чтение недоступно | Управляемые сервисы AWS. SQS Standard допускает дубликаты и изменение порядка |
| NATS + JetStream | Обмен событиями по темам с хранением | Подписки по subject, экземпляры могут делить работу через общий consumer | С сохранённой позиции в пределах политики хранения | Свой сервер или управляемый сервис. При WorkQueuePolicy сообщение удаляется после подтверждения |
| Redis Streams | Поток задач или событий рядом с приложением на Redis | Группа делит записи между участниками, разные группы читают независимо | По ID, пока запись хранится | Свой Redis или управляемый сервис. Нужно настроить обрезку истории и разбор зависших доставок |

- RabbitMQ Streams хранит журнал, который можно перечитывать до истечения срока хранения или достижения лимита размера.
- Redis Streams хранит записи. Redis Pub/Sub доставляет только подключённым подписчикам, без сохранённой истории.

## Когда выбирать RabbitMQ

| Ситуация | Что рассмотреть |
| --- | --- |
| Готовим документы в фоне, события заказа расходятся по разным правилам | RabbitMQ. Несколько обработчиков делят нагрузку, правила привязок управляют рассылкой |
| Храним события долго и регулярно пересчитываем данные с прошлой позиции | Kafka или RabbitMQ Streams. Нужен журнал с управляемым хранением и повторным чтением |
| При оформлении нужна цена доставки прямо сейчас | Синхронный HTTP-запрос с ограничением времени ожидания |
