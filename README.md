# RabbitMQ на Python — очередь задач и события заказа

Учебный проект показывает, как два воркера делят очередь `order_tasks` и как RabbitMQ доставляет одно событие заказа в несколько очередей. Можно запустить обе демонстрации из терминала и следить за доставкой в веб-панели.

## Быстрый старт

### 1. Подготовьте окружение

Для примеров нужен Python 3.10 или новее. Откройте терминал в корне репозитория, где находится `pyproject.toml`. Понадобится `uv`. В Windows его можно установить командой `winget install --id=astral-sh.uv -e`, в macOS через Homebrew — `brew install uv`. После установки откройте новый терминал. [Установка uv для всех платформ](https://docs.astral.sh/uv/getting-started/installation/)

```shell
uv sync --locked
uv run rabbit-events --help
```

Первая команда создаёт `.venv` и устанавливает проект, Pika и Ruff в версиях из `uv.lock`. Вторая выводит доступные команды для событий. Для просмотра справки брокер можно ещё не запускать. Во всех примерах `uv run` сам выбирает окружение проекта.

### 2. Запустите RabbitMQ

Для этого варианта нужен запущенный Docker Engine или Docker Desktop в режиме Linux-контейнеров. Для первого запуска выполните команду ниже.

```shell
docker run -d --name rabbitmq-lab --hostname rabbitmq-lab -p 127.0.0.1:5672:5672 -p 127.0.0.1:15672:15672 -e RABBITMQ_DEFAULT_USER=demo -e RABBITMQ_DEFAULT_PASS=demo-local rabbitmq:4-management
```

Docker загрузит образ и запустит брокер с веб-панелью. Порты опубликованы только на локальном адресе компьютера. После запуска дождитесь открытия страницы входа. При необходимости посмотрите журнал командой `docker logs rabbitmq-lab`. [Открыть локальную панель RabbitMQ](http://127.0.0.1:15672)

| Параметр | Значение для примеров | Где используется |
|---|---|---|
| Сервер и порт AMQP | `127.0.0.1:5672` | Скрипты отправляют и получают сообщения через Pika. |
| Порт веб-панели | `15672`, протокол HTTP | В браузере можно посмотреть очереди, привязки, число сообщений и воркеров. |
| Учебный логин и пароль | `demo` / `demo-local` | Команда Docker создаёт пользователя при первой инициализации брокера. Эти же данные заданы в Python. |
| Виртуальный хост | `/` | В этом пространстве RabbitMQ создаются очереди и обменник проекта. |

**Если RabbitMQ уже установлен**, проверьте адрес, `port`, `virtual_host` и `pika.PlainCredentials(...)` в [lab_connection.py](src/rabbitmq_lab/lab_connection.py). Созданному на брокере пользователю нужны права объявлять ресурсы (`configure`), записывать (`write`) и читать (`read`) в выбранном виртуальном хосте. Для веб-панели включите плагин `rabbitmq_management` и используйте аккаунт с доступом к панели. В браузере можно войти под другим пользователем. Изменение пароля в Python меняет данные, которые отправит клиент при следующем подключении.

## Сценарий 1. Как два воркера делят четыре задачи

Откройте **три терминала** в корне проекта. Начните с пустой очереди и остановленных воркеров, чтобы увидеть, как очередь заполняется. Параметры команды — длительность задачи в секундах и один или несколько идентификаторов.

**Терминал 1 — отправить задачи**

```shell
uv run rabbit-publish 12 TASK-101 TASK-102 TASK-103 TASK-104
```

Отправитель создаст очередь `order_tasks` и опубликует четыре отдельных сообщения. Первое содержит `{"task_id": "TASK-101", "seconds": 12}`. Число `12` относится к обработке каждой задачи. Отправитель завершится, как только получит подтверждения публикации. Для первой задачи появится строка.

```text
CONFIRMED queue=order_tasks task=TASK-101 seconds=12
```

Откройте **Queues and Streams → order_tasks** и дождитесь обновления показателей. Пока воркеры остановлены, ожидается `Ready = 4` и `Consumers = 0`.

**Терминал 2 — запустить первого воркера**

```shell
uv run rabbit-worker worker-A
```

**Терминал 3 — запустить второго воркера**

```shell
uv run rabbit-worker worker-B
```

У каждого процесса свой PID. Для одной задачи вывод воркера выглядит так.

```text
WAIT worker=worker-A pid=12480 queue=order_tasks
START worker=worker-A pid=12480 queue=order_tasks task=TASK-101 seconds=12 redelivered=False
DONE worker=worker-A task=TASK-101
ACK_SENT worker=worker-A task=TASK-101
```

`prefetch_count=1` позволяет каждому воркеру иметь одну неподтверждённую задачу. Сразу после подключения обоих воркеров можно увидеть две задачи в обработке и две в ожидании, если первые задачи ещё выполняются. Порядок назначения `TASK-101`–`TASK-104` зависит от того, когда воркеры подключатся и освободятся.

| Показатель очереди | Как его читать |
|---|---|
| `Ready` | Сколько сообщений ждут выдачи. |
| `Unacked` | Сколько сообщений уже доставлены, но брокер ещё ждёт подтверждения от воркеров. |
| `Consumers` | Сколько потребителей подписаны на очередь. По завершении задач воркеры продолжают ждать. |

### Как увидеть повторную доставку

1. Дождитесь, пока воркеры обработают все четыре предыдущие задачи и показатели `Ready` и `Unacked` станут равны нулю. Оба воркера оставьте запущенными.
2. В терминале отправителя выполните `uv run rabbit-publish 60 TASK-105`.
3. Найдите терминал, где появилась строка `START` для `TASK-105`. Завершите **именно этот воркер** с помощью `Ctrl+C` до появления `DONE`. Соединение второго воркера должно оставаться открытым.
4. Когда брокер обнаружит закрытие соединения, в терминале оставшегося воркера ожидается `START` для того же `TASK-105` с `redelivered=True`. После обработки появится `ACK_SENT`.

У подтверждений разный смысл. `CONFIRMED` выводит отправитель после подтверждения публикации брокером. `DONE` — локальная запись об окончании работы. `ACK_SENT` воркер печатает после вызова `basic_ack()`. Если работа уже выполнена, а подтверждение потеряно, та же задача может прийти снова. Идентификаторы проверяются на уникальность только внутри одной команды отправителя. Между запусками проект дубликаты не отслеживает.

## Сценарий 2. Как одно событие попадает в две очереди

Для этой демонстрации достаточно одного терминала. Скрипт `events.py` работает с отдельными очередями, поэтому воркеры первого сценария на результат не влияют.

```shell
uv run rabbit-events setup
uv run rabbit-events publish
```

`setup` создаёт обменник `orders.events` типа `topic` и связывает с ним две очереди. `publish` отправляет три события для одного заказа `ORD-1042`. Тип события передаётся в ключе маршрутизации (`routing_key`), а тело содержит `event_id` и `order_id`.

| Событие | Ключ маршрутизации | `order_audit`, шаблон `order.*` | `order_notifications`, ключ `order.created` |
|---|---|---|---|
| `EVT-201` | `order.created` | Получит | Получит |
| `EVT-202` | `order.cancelled` | Получит | — |
| `EVT-203` | `payment.failed` | — | — |

В шаблоне `order.*` звёздочка заменяет ровно одно слово после точки. Первые два события подходят очереди аудита. Очередь уведомлений получает только событие создания. Для `payment.failed` подходящих привязок нет, поэтому флаг `mandatory=True` заставляет брокер вернуть публикацию. При заданных привязках ожидается такой вывод.

```text
CONFIRMED event=EVT-201 key=order.created
CONFIRMED event=EVT-202 key=order.cancelled
RETURN event=EVT-203 key=payment.failed reason=NO_ROUTE
```

Теперь прочитайте очереди.

```shell
uv run rabbit-events read order_audit
uv run rabbit-events read order_notifications
```

Если до публикации очереди были пусты, первая команда завершится строкой `EMPTY queue=order_audit read=2`, вторая — `EMPTY queue=order_notifications read=1`. Чтение очереди аудита не затрагивает копию `EVT-201` в уведомлениях. Команда `read` подтверждает каждое прочитанное сообщение и выходит, когда очередь опустеет. Повторный `read` без новых событий покажет `read=0`. Чтобы повторить демонстрацию, снова выполните `publish`.

## Как устроен код

| Файл | За что отвечает |
|---|---|
| [lab_connection.py](src/rabbitmq_lab/lab_connection.py) | `open_connection()` передаёт адрес, виртуальный хост и учётные данные в `pika.BlockingConnection`. Это общие настройки для трёх скриптов. |
| [tasks_publish.py](src/rabbitmq_lab/tasks_publish.py) | `main()` принимает длительность от 1 до 120 секунд и неповторяющиеся ID в одной команде. Для каждой задачи публикует JSON через встроенный обменник `exchange=""` с ключом `order_tasks`. |
| [task_worker.py](src/rabbitmq_lab/task_worker.py) | `main()` подписывает `worker-A` или `worker-B` на очередь. Вложенная функция `handle_task(...)` читает JSON, имитирует работу через `connection.sleep(seconds)` и отправляет ручное подтверждение. |
| [events.py](src/rabbitmq_lab/events.py) | `main()` выбирает подкоманду. `setup()` объявляет обменник и привязки, `publish()` публикует события и обрабатывает возврат, `read()` читает выбранную очередь до опустошения. |
| [pyproject.toml](pyproject.toml) | Зависимости, три команды запуска и правила Ruff. Стандартные модули Python `argparse`, `json` и `os` используются для аргументов командной строки, сообщений и PID. |
| [uv.lock](uv.lock) | Точные версии пакетов для воспроизводимой установки. |
| [requirements.txt](requirements.txt) | Установка того же пакета и его зависимостей через `pip install -r requirements.txt`. |
| [rabbitmq-presentation.md](docs/rabbitmq-presentation.md) | Материалы доклада с пояснениями обменников, подтверждений и отличий очередей от журналов событий. |

Очереди объявлены как `durable=True` и `classic`, а сообщения помечены `delivery_mode=2` для сохранения при перезапуске брокера. Обменник `orders.events` также объявлен сохраняемым. На сохранность данных влияет и то, остаётся ли доступным хранилище самого брокера.

## Проверка кода

Из корня репозитория выполните две команды. Первая проверяет ошибки Python, порядок импортов, распространённые проблемные конструкции и устаревший синтаксис. Вторая проверяет единообразие форматирования.

```shell
uv run ruff check .
uv run ruff format --check .
```

Чтобы применить доступные безопасные исправления и отформатировать код, выполните `uv run ruff check --fix .`, затем `uv run ruff format .`. После изменения зависимостей обновите `uv.lock` командой `uv lock` и включите его в тот же коммит, что и `pyproject.toml`.

При отправке коммита или открытии pull request GitHub Actions проверяет lock-файл, линтер, форматирование и запуск справки у всех трёх команд. [Конфигурация проверок](.github/workflows/checks.yml)

## Частые вопросы

| Что видно | Что проверить |
|---|---|
| `ModuleNotFoundError: No module named 'pika'` | Выполните `uv sync --locked` в каталоге с `pyproject.toml` и запускайте команды через `uv run`. |
| `AMQPConnectionError` или отказ в соединении | Проверьте, что RabbitMQ завершил запуск и что в `lab_connection.py` указан доступный AMQP-порт `5672`. Если Python и брокер находятся на разных машинах или в разных ВМ, `127.0.0.1` указывает на машину с Python. Используйте доступный адрес брокера или настроенный проброс порта. |
| Ошибка входа или `ACCESS_REFUSED` | Сверьте логин, пароль и виртуальный хост с конфигурацией брокера. Для ошибки при объявлении очереди или публикации отдельно проверьте права пользователя на эту операцию. |
| Python подключается, а панель не открывается | Откройте `http://127.0.0.1:15672`. На собственном брокере проверьте плагин `rabbitmq_management` и доступ к его HTTP-порту. |
| `NOT_FOUND` при публикации событий или чтении очереди | Сначала выполните `uv run rabbit-events setup` на том же брокере и виртуальном хосте. |
| В панели `Ready = 0` сразу после отправки | Если уже запущен воркер, он мог сразу забрать задачу. Проверьте `Unacked` и строки `START` / `ACK_SENT` в его терминале. |
| После двух запусков `publish` сообщений вдвое больше | Каждый запуск публикует новую партию. Для следующей демонстрации сначала дочитайте обе очереди командой `read`. |

Для справки по допустимым аргументам выполните `uv run rabbit-publish --help`, `uv run rabbit-worker --help` или `uv run rabbit-events read --help`.

## Остановка и следующий запуск

Остановите воркеры с помощью `Ctrl+C`. Если брокер создан по инструкции Docker, остановите контейнер командой `docker stop rabbitmq-lab`. При следующем запуске используйте `docker start rabbitmq-lab`. Так будут использованы существующий контейнер и его данные.
